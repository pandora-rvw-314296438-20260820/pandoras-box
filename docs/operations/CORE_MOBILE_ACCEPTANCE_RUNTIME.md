# Core mobile acceptance runtime

`core_acceptance_v1` is an explicit, source-bound profile for private generic/Core Pandora testing in an isolated Supabase target. It preserves the production profile and does not promote an acceptance APK, database, bridge deployment or test result into a production release. Canonical source is `pandora-rvw-314296438-20260820/pandoras-box`; tenant-specific implementations are not Core acceptance evidence.

The mobile startup validator, Python producer and server validator share one compact UTF-8 JSON binding, in this key order: `profile`, `sourceSha`, `supabaseProjectRef`, `supabaseUrl`, `publishableKeySha256`, `organizationId`, `ownerApiBaseUrl`, `projectRuntimeApiBaseUrl`, `memoryMode`. Use the producer helpers and shared fixture; do not hand-normalize or append fields. URLs derive from the isolated project ref, `memoryMode` is `unavailable`, and the SHA-256 binds the exact JSON. Source, target, organization and public-client-key digest must agree. Main and Memory project refs, malformed identifiers, incomplete settings and orphan acceptance settings are rejected.

## Protected configuration

The GitHub environment is `pandora-core-mobile-qa`. Workflows read its actual required-reviewer protection rules; the environment name alone is insufficient.

| Name | Storage and purpose |
| --- | --- |
| `PANDORA_CORE_QA_RUNTIME_PROFILE` | Environment variable: `core_acceptance_v1`. |
| `PANDORA_CORE_QA_REVIEWED_SOURCE_SHA` | Environment variable: independently reviewed, exact candidate commit. |
| `PANDORA_CORE_QA_TARGET_JSON` | Environment variable: canonical public binding described above. Contains a key digest, never a key. |
| `PANDORA_CORE_QA_CONFIG_SHA256` | Environment variable: digest of that binding. |
| `PANDORA_CORE_QA_SUPABASE_PUBLISHABLE_KEY` | Environment secret consumed only by the Android producer. Must be a public client key, or a target-bound legacy `anon` JWT; never a service-role key. |
| `PANDORA_CORE_QA_EMAIL`, `PANDORA_CORE_QA_PASSWORD` | Environment secrets for an actual isolated-target Auth account used by the authenticated native journey. |
| `VERCEL_TOKEN` | Secret consumed by the restricted bridge deployment workflow. |

The producer writes private Dart defines to a permissions-restricted temporary file, removes it after the build, and exports only the public binding and artifact digests. It supplies the existing `PANDORA_SUPABASE_URL`, `PANDORA_SUPABASE_PUBLISHABLE_KEY`, `PANDORA_ORGANIZATION_ID`, `PANDORA_SOURCE_REVISION`, `PANDORA_OWNER_API_BASE_URL` and `PANDORA_PROJECT_RUNTIME_API_BASE_URL` defines. Never print, upload or commit the private defines, login values, service credentials, workload tokens or chat bodies.

Server configuration uses `PANDORA_RUNTIME_PROFILE` and `PANDORA_ACCEPTANCE_` fields with suffixes `SUPABASE_PROJECT_REF`, `ORGANIZATION_ID`, `SOURCE_SHA`, `PUBLISHABLE_KEY_SHA256`, `CONFIG_SHA256`. Edge functions must see their actual matching `SUPABASE_URL`; platform service credentials remain server-side. Chat additionally requires `PANDORA_ACCEPTANCE_BRIDGE_ORIGIN`, the verified immutable deployment origin. Control validates that shared Edge setting without routing through it. The origin is bound by the deployment receipt after deployment, rather than included in the earlier base digest.

## Provision and run

1. **Resolve the actual isolated target.** Identify the Supabase provider/billing organization and satisfy the provider tool's actual organization and branch-cost confirmation prerequisite before creating a branch. That provider organization identifier is distinct from the application's `public.organizations.id` UUID in the binding. Authorized synthetic Core fixtures do not require an invented additional blanket approval. They still require a real branch, real Auth user, valid application organization membership and applicable Core permissions. Reconcile or explicitly qualify inherited migration/source parity and sole-writer ownership; do not edit the migration ledger or bypass below-tip checks.

2. **Freeze source and deploy the restricted reader first.** Populate the protected source/target binding, then dispatch [`task-146-prebuilt-vercel-deploy.yml`](../../.github/workflows/task-146-prebuilt-vercel-deploy.yml) at that exact commit with `source_sha` equal to the workflow commit and `runtime_profile=core_acceptance_v1`. The source-built output contains only the Bedrock entrypoint, its traced dependencies and public receipt: no inherited crons, unrelated APIs or rewrites. Deployment uses `--prebuilt --prod --skip-domain`; never alias or promote it. The verifier reads actual Vercel ownership, deployment metadata, aliases and scheduler state, compares the served receipt byte-for-byte, and checks an empty-ticket denial with matching runtime headers. This denial does not claim a ticket, obtain workload identity or prove provider inference.

3. **Prepare the branch runtime.** Apply the reviewed additive migrations `20261003170000` through `20261003170300` from `supabase/migrations`, then the branch-only [`core_acceptance_ticket_binding_v1.sql`](../../supabase/acceptance/core_acceptance_ticket_binding_v1.sql). The latter is deliberately outside the production migration ledger and creates no Auth users or fabricated provider verification. Create or verify the isolated application organization before inserting the binding: `private.pandora_core_acceptance_runtime_config.organization_id` is a foreign key. Install the validated canonical binding and branch-only Core/Auth fixtures, including the QA account's active owner/admin membership, `private.pandora_core_config`, and appropriate active `private.pandora_operator_grants`. Deploy the exact-source `pandora-intelligence-chat` and `mcpmaster-supabase-control` functions with matching profile settings; verify required owner/runtime APIs at their derived branch URLs. Confirm real model-catalog eligibility and one-time ticket issuance/claim, with organization/config/source checks, before treating inference as available.

4. **Build the bound APK.** Dispatch [`pandora-mobile-integration.yml`](../../.github/workflows/pandora-mobile-integration.yml) at the reviewed source with `runtime_profile=core_acceptance_v1`. Retain the successful run ID, artifact ID, source manifest, public acceptance binding, archive digest and debug/profile APK digests. Acceptance artifacts have the `pandora-mobile-android-core-acceptance-` prefix. A compiled APK or successful producer job is build evidence only.

5. **Install those same bytes and exercise the journey.** Dispatch [`pandora-core-mobile-journey.yml`](../../.github/workflows/pandora-core-mobile-journey.yml) with `source_sha`, `build_run_id`, `artifact_id`, `build_kind` (`debug` or `profile`), `runtime_profile=core_acceptance_v1`, matching `config_sha256`, and `mode=authenticated`. It validates protected source/target/login prerequisites and installs the existing artifact without rebuilding, on small and tall Android viewports. Preserve artifact, installation and journey receipts with scoped evidence. `mode=platform` proves only the interactions it actually exercises; it cannot substitute for authenticated continuity, provider recovery, streaming or the continuous chat journey.

## Runtime and release boundaries

Acceptance transport metadata is `x-pandora-runtime-profile`, `x-pandora-config-sha256`, and `x-pandora-source-sha`. It binds requests and responses; it grants no authorization. Real user JWT validation, single-use database tickets, Vercel workload OIDC and provider authorization still apply. The bridge shares the existing **production workload identity** because it is deployed in the production-classified Vercel environment with domain assignment skipped. Report `shared_production_workload_identity`; do not claim isolated IAM, preview identity, or provider success from deployment readiness. Production aliases and scheduler state must remain unchanged. Live STS trust and `bedrock:InvokeModelWithResponseStream` permission for the source-defined role in `src/providers/aws-bedrock-catalog.js` and region `us-east-1` remain unverified until actual policy readback and authorized invocation provide evidence.

Mobile startup validates before attribution or networking. Its acceptance SDK guard verifies responses before decoding chat events, confines supported requests to the branch and rejects redirects. Production initialization remains unchanged. Acceptance Memory returns unavailable before token access or HTTP construction, and the restricted bridge includes no Memory route; no production Memory read is part of this profile.

Keep test results and runtime/deployment status in exact-source receipts, not mutable claims in this runbook. Configuration, transport and startup tests establish their scoped behavior, not authenticated native or production acceptance. Preserve failed and unverified stages explicitly.

Only after the required source checks, independent review and continuous authenticated acceptance journey pass should the authorized change advance to `main`. Reconcile any main drift, rebuild the resulting exact main commit with the **production** profile, and verify the production backend and exact artifact journey before making a production-readiness claim. Acceptance evidence remains tied to its tested source and target. [`pandora-mobile-release.yml`](../../.github/workflows/pandora-mobile-release.yml) requires `source_sha` and `mobile_run_id` from a successful main-push producer, rejects acceptance artifacts, and publishes a validation prerelease; that publication itself does not assert production or physical-device verification.
